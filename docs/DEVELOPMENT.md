# Developing Cheese

```sh
make generate   # regenerate Cheese.xcodeproj from project.yml (XcodeGen)
make build      # Debug build
make test       # unit tests (Swift Testing), then the Release app size budget
make test-integration   # also the slower Files tests that render through WebKit
make run        # build and launch
make release    # Release build → dist/Cheese.zip + SHA-256
scripts/release.sh 2.4 [--publish]   # bump the version, package, and print (or run) the gh release command
```

The Xcode project is generated, so edit `project.yml` rather than `Cheese.xcodeproj`. The code is organised by feature (`Clipboard/`, `Capture/`, `OCR/`, `ScrollCapture/`, `Recording/`, `Windows/`, `Editor/`, `Draw/`, `QR/`, `Caffeinate/`, `AppHotkeys/`, `Palette/`, `Files/`, `Shelf/`, `Share/`, `AppSweep/`, `TerminalTrace/`, `Hush/`, `Sweep/`, `Update/`, `Welcome/`, `Settings/`), with shared UI in `CheeseUI/` (see [DESIGN.md](DESIGN.md)), with the wiring in `App/`: every action lives once in an `ActionRegistry` that the menu, hotkeys and command palette all read, and each feature is a `CheeseModule` that can be switched off. Pure logic (fuzzy matching, stitching, sticky-header detection, snap geometry, display coordinate conversion, canvas history, stroke smoothing, the ink engine (1€ filter and variable-width outlines), shape recognition, the radial menu, hit-testing, draw mode's keyboard rules, QR payload planning, share-link rules, Caffeinate scheduling and session rules, hotkey suggestions, palette ranking, and the Files tools' applicability, output naming, page ranges, split and compression planning, layout analysis, table detection and resize math, Stage Manager and live-Dock fill frames, Auto-Kill planning, Terminal Trace parsing, clipboard multi-selection and batch payloads, Sweep's session and Esc hold, Hush's policy and share-indicator rules, the recording plan, clock and GIF frame plan, the scrolling-capture thumbnail, and the updater's version, release, checksum and install-location rules) has no AppKit dependencies and is covered by unit tests. Caffeinate's lid-closed root helper is a shell script generated by `CaffeinateHelperFiles`; its tests run the real script against stand-in `pmset`, `ioreg` and `ps` commands, so every line that would run as root is exercised.

The Finder submenu (`CheeseFinderExtension`) and the Share menu entry (`CheeseShareExtension`) are separate, sandboxed targets that only hand jobs to the app through the App Group. Cheese Share's LocalSend support is described in [LOCALSEND.md](LOCALSEND.md). The vendored JavaScript renderers live in `Cheese/Resources/Renderers/` with exact versions, licenses and the reasons for each choice in [`VENDORED.md`](../Cheese/Resources/Renderers/VENDORED.md); a test keeps them under 3 MB. The Files test fixtures are all self-made by `Design/make-files-fixtures.swift` and `.mjs`.

The windows Hush recognizes as a meeting app sharing the screen live in [`ShareIndicators.json`](../Cheese/Hush/ShareIndicators.json) (bundle IDs plus title fragments). Add an app there in a pull request; no code changes needed.

Known global shortcuts that the hotkey suggester should never propose live in [`ReservedShortcuts.json`](../Cheese/AppHotkeys/ReservedShortcuts.json). Add an entry there in a pull request; no code changes needed.

## Releases and the updater

**Publishing a release:** `scripts/release.sh 2.4` sets `MARKETING_VERSION` to 2.4 and adds one to `CURRENT_PROJECT_VERSION` in `project.yml`, runs `scripts/package.sh` (Release build, `codesign --verify`, `ditto` zip, SHA-256) and prints the command to publish:

```sh
gh release create v2.4 dist/Cheese.zip dist/Cheese.zip.sha256 --title "Cheese 2.4" --generate-notes
```

With `--publish` (from a clean `main`) it also commits the bump as "Cheese 2.4", pushes, and creates the release. Tags are `v` + the version; the updater compares them part by part, so `2.4` = `2.4.0` < `2.4.1` < `2.10`.

Keep the assets named `Cheese.zip` and `Cheese.zip.sha256`: the install script and download links point at `releases/latest/download/Cheese.zip`, and the in-app updater won't install a release without the checksum. Releases stay signed with the Apple Development identity from `project.yml`: the updater only installs an app that meets `anchor apple generic and identifier "com.maanitgupta.cheese" and certificate leaf[subject.OU] = "<the running copy's team>"`, and the same signature keeps users' Screen Recording and Accessibility grants.

**How updating works** (`Cheese/Update/`): `UpdateService` asks `api.github.com/repos/maanit-gupta/Cheese/releases/latest` 3 s after launch and whenever 12 hours have passed (looked at hourly, so a Mac that slept catches up). `UpdatePlanner` (pure) turns the answer into an offer: published, not a pre-release, newer than the running version. Installing downloads the archive and checksum into `$TMPDIR/CheeseUpdate-<uuid>/`, compares SHA-256, unpacks with `ditto`, and checks the bundle identifier, version, executable and signature before anything outside that folder changes. Then it starts `UpdateSwapScript` detached (`nohup sh swap.sh <pid> <app> <new app> <staging> <log>`, paths as arguments, never as shell text) and quits; the script waits up to 15 s for Cheese to exit, moves the old app to `Cheese.app.backup`, moves the new one in (restoring the backup if that fails), clears extended attributes, deletes the staging folder and reopens Cheese. Its tests run the real script on scratch folders, including paths with quotes and `$(…)` in them.

To try the whole flow without publishing: build a newer archive (`scripts/release.sh 2.4`, then `git checkout project.yml`), serve it with `python3 -m http.server 8765 --bind 127.0.0.1 --directory dist`, and run

```sh
TEST_RUNNER_UPDATE_ARCHIVE_BASE=http://127.0.0.1:8765 xcodebuild -project Cheese.xcodeproj -scheme Cheese \
    -destination 'platform=macOS' -derivedDataPath build/DerivedData test -only-testing:CheeseTests/UpdateEndToEndTests
```

which stages the real archive (download, checksum, signature) and swaps it into a scratch copy of the app. Delete that `dist/` afterwards so it isn't published by mistake.

## Contributing

Bug reports and pull requests are welcome. Please open an issue first for anything big. Run `make test` before sending a PR. The build treats warnings as errors.

## App size budget

`make test` ends with `scripts/check-size.sh`, which builds Release and fails if `Cheese.app` is more than 2 MB larger than `scripts/size-baseline.txt` (the 2.5 Release bundle with screen recording, in bytes). Raise the baseline only on purpose, and say why in the commit.

## Cheese Share over real HTTPS

`make test` covers Cheese Share over loopback sockets (LocalSend send/receive, messages, the phone
page) without touching the Keychain. To also run a real HTTPS round trip with a Keychain identity made
the way the app makes its own (under a throwaway label, deleted afterwards):

```sh
TEST_RUNNER_SHARE_KEYCHAIN=1 xcodebuild -project Cheese.xcodeproj -scheme Cheese -destination 'platform=macOS' \
    -derivedDataPath build/DerivedData test -only-testing:CheeseTests/ShareHTTPSTests
```

`open cheese://share` opens the Share panel, which starts the listeners; `curl -k https://<mac-ip>:53317/api/localsend/v2/info`
then shows what LocalSend devices see.

## The phone page in Safari's engine

`PhonePageInBrowserTests` serves the real phone page and waits; `scripts/phone-page-webkit.mjs` drives it in
WebKit as an iPhone 13 (Playwright, installed for the promo render): upload a photo, send text, download
what the Mac offers and copy its text over plain HTTP. It leaves `webkit.png` and `webkit-dark.png` in the
folder. Run both together:

```sh
D=$(mktemp -d)
TEST_RUNNER_PAGE_SERVE=$D xcodebuild -project Cheese.xcodeproj -scheme Cheese -destination 'platform=macOS' \
    -derivedDataPath build/DerivedData test -only-testing:CheeseTests/PhonePageInBrowserTests &
node scripts/phone-page-webkit.mjs $D
```

## A real screen recording

`RecordingLiveTests` records three seconds of the main display through ScreenCaptureKit (with a pause in the middle), checks the joined movie has one video and one system-audio track, then makes a GIF from it. It needs Screen Recording for the test host:

```sh
TEST_RUNNER_RECORDING_LIVE=1 xcodebuild -project Cheese.xcodeproj -scheme Cheese -destination 'platform=macOS' \
  -derivedDataPath build/DerivedData test -only-testing:CheeseTests/RecordingLiveTests
```

## Panels without a screen

`PanelSnapshotTests` renders the drop hub, the Share panel (staged, with nearby devices, and with a received
file) and the QR panel to PNGs (light and dark) through an offscreen hosting view, to check their layout from a
terminal and to make the README stills. Menus and buttons are drawn as in the app. If Cheese itself is running
with Share open, it holds LocalSend's port, so the panel reports that discovery failed; quit it first for a clean still.

```sh
TEST_RUNNER_SNAPSHOT_DIR=$(mktemp -d) xcodebuild -project Cheese.xcodeproj -scheme Cheese -destination 'platform=macOS' \
    -derivedDataPath build/DerivedData test -only-testing:CheeseTests/PanelSnapshotTests
```

## Promo video

`Design/promo/promo.html` is a deterministic animation: `window.seek(t)` draws the frame at time `t`, so every
render is identical. Scenes are listed in order with a length each and play back to back, so adding one shifts
the rest automatically. `render.mjs` looks for Playwright's Chromium in `~/Library/Caches/ms-playwright`; set
`CHROMIUM` to use another binary. Frames render at `SCALE` × 1080p (default 2) and are downscaled, which keeps
text crisp; page errors fail the render.

```sh
cd Design/promo
npm install --no-save playwright-core && npx playwright install chromium
node render.mjs stills 15 23.3         # spot-check frames → stills/ (SCALE=1 is quicker)
node render.mjs mp4 30                 # frames piped into ffmpeg → docs/media/cheese-promo.mp4 (2560×1440)
ffmpeg -i ../../docs/media/cheese-promo.mp4 -vf "fps=12,scale=880:-1:flags=lanczos,split[a][b];[a]palettegen=max_colors=160:stats_mode=diff[p];[b][p]paletteuse=dither=bayer:bayer_scale=4:diff_mode=rectangle" ../../docs/demo.gif
```

`node render.mjs video 30` still writes numbered PNGs to `frames/` instead (`START=<frame>` resumes), for editing
in another tool. `OUT_W`/`OUT_H` change the MP4's size.
